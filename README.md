# LEXBRIDGE Knowledge Repository

The single source of truth for LEXBRIDGE's Egyptian legal knowledge base.
This repository holds **data only** — no application code, no Knowledge
Engine, no search infrastructure. The website (`lexbridge-website`) consumes
this repository's `knowledge/` folder to build its search indexes; it never
stores a duplicate copy of the legal data long-term.

## Adding a new legal dataset (future expansion)

1. Create `knowledge/<new_collection>/` and add real JSON records — no mock/invented data.
2. Add one entry to `schemas/document-types.registry.json` describing the new collection.
3. Run `python3 scripts/build_index.py` to regenerate the manifest and confirm zero drift / zero unregistered folders.
4. Commit and push.
5. On the website side, run `npx tsx scripts/knowledge-engine/reindexAll.ts <path-to-this-repo>/knowledge` — it reads the same registry file, so no website code changes are needed unless the new collection needs a genuinely new search type (see registry's `how_to_add_a_type`).

No hardcoded paths or document types live in the website's ingestion code —
everything is driven by `schemas/document-types.registry.json`.

## Record schema

Every record in `knowledge/` follows one of two shapes documented in
`schemas/`:

- **`legal_article`** (laws/): flat shape — `law_name`, `law_number`, `law_year`, `article_number`, `content`, plus `book`/`chapter`/`section`/`topic` where the source law was structured enough to capture them.
- **Everything else** (judgments/principles/procedures/deadlines/templates): `{ id, type, category, title, content, keywords, citations, related_ids, metadata, source_fields }`.

Both shapes carry six relation arrays added during the Sprint (Knowledge
Graph v1) merge: `related_articles`, `related_judgments`, `related_defenses`,
`related_procedures`, `related_contracts`, `related_principles`. Most are
still empty for older record types — populating them further is a future,
separate initiative, not part of this reorganization.

## Known data-quality notes (carried over, not hidden)

- 31 duplicate IDs pre-date this reorganization (documented origin: `civil_all.json` source file — see `metadata/PROVENANCE.md`).
- 56,783 of 65,395 records have zero populated relations; citation linking only ran where an explicit article number + identifiable law/domain was present in the source text (no semantic guessing — see `knowledge/references/legacy_reports` for the full methodology write-up).
- `defenses` and `contracts` are registered as *planned* collection types with 0 records — no first-party standalone data exists for either yet. Derived `defense` records ARE produced at search-index build time from `judgment_principle.source_fields.defense_args`; that logic lives in the website's Knowledge Engine ingestion step, not duplicated here.
- Some `laws_db` source PDFs were scanned images with no extractable text and were excluded pending OCR (see `knowledge/references/legacy_indexes/laws_db/_pending_ocr_scanned_pdfs.json`).
